Background & Motivation

The Problem

Backend services commonly fail in two major scenarios:

1. Traffic Surges: Too many requests arrive simultaneously, exhausting thread pools, CPU, or database connection pools.
2. Cascading Dependency Failures: A downstream service starts failing repeatedly, causing timeouts and backpressure to propagate upstream through the system.

Without built-in fault tolerance, these failures cascade into widespread system outages. Resilient Gateway provides dual layers of protection:

Rate Limiting

Strictly controls and throttles incoming traffic to match backend capacity limits.

Circuit Breaking

Stops repeatedly calling a failing dependency, allowing it time to heal while serving fallback responses.

Component Deep Dive

Rate Limiting: Token Bucket Algorithm

Each client is associated with a bucket containing a limited number of tokens. A request consumes a token, while tokens are continuously replenished at a configured rate. If no token is available, the request is rejected immediately.

Distributed Design

Why Redis?

An in-memory rate limiter works only inside a single process. In a distributed multi-instance deployment:

• Instance A → Tracks its own local counter
• Instance B → Tracks a different counter
• Instance C → Tracks another counter

A centralized, low-latency Redis cluster allows all gateway instances to share state and enforce the same global rate limit accurately across the entire cluster.

Global Rate Limit Enforcement

Concurrency Control

Why Redis Lua Scripts?

A naive implementation might perform three separate commands: GET → calculate tokens → SET.

Under high concurrency, multiple processes can read the same token count before either updates it, creating severe race conditions and allowing traffic bursts to breach configured limits.

Redis Lua scripts execute directly on the Redis server as a single atomic transaction. The token check, replenishment calculation, and state mutation happen in one isolated step without requiring distributed locks.

Closed

Requests flow normally to downstream services. Consecutive failures and latency spikes are continuously monitored.

Open

Requests are rejected immediately or served fallback responses without making calls to the failing upstream service.

Half-Open

After a configured recovery timeout, a small trial percentage of traffic is routed to probe whether the service has recovered.

System Analysis

Engineering Trade-offs

Token Bucket vs Sliding Window

  • Token Bucket: Highly efficient O(1) time complexity
  • Token Bucket: Gracefully accommodates controlled bursts
  • Token Bucket: Minimal memory state representation
  • Sliding Window: More precise traffic smoothing at the cost of higher state complexity

In-Memory vs Redis

  • In-Memory: Zero network overhead, extremely fast execution
  • In-Memory: Fails to synchronize state across horizontal instances
  • Redis: Shared global state across distributed replicas
  • Redis: Atomic Lua scripts prevent concurrency race conditions
  • Redis: Adds a minor network hop dependency
